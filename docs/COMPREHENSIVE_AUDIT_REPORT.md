# Linux System Hardener - Comprehensive Audit Report

> **Date**: 2026-02-17
> **Scope**: Full codebase and documentation analysis
> **Purpose**: Identify all bugs, issues, and improvements; explain why hardening is not working
> **Status**: Read-only analysis - NO changes made

---

## Executive Summary

The analysis dispatched 10 parallel investigation agents across every layer of the project:
core engine, CLI, GUI/Tauri, plugins, build system, tests, CI/CD, and documentation.

**The core finding**: The hardening engine itself IS functional and DOES write real changes
to the system when run correctly via `sudo hardener apply --all`. However, **multiple
compounding bugs** in the GUI-to-CLI communication pipeline, error reporting, and plugin
logic cause hardening to silently fail or produce incorrect results in practice.

The issues fall into three categories:
1. **GUI Apply Pipeline is Broken** (hardening never reaches the system via the desktop app)
2. **Plugin-Level Logic Bugs** (some plugins apply wrong rules or report false success)
3. **Infrastructure Debt** (uncommitted fixes, documentation drift, CI gaps)

## TIER 1: CRITICAL BUGS (Hardening Broken)

### BUG-01: JSON Deserialization Mismatch - GUI Apply Always Fails — FIXED

**Severity**: CRITICAL | **Status**: Fixed (commit b9ce945)
**Files**:
- `crates/hardener-cli/src/output.rs:98-102`
- `src-tauri/src/commands.rs:257-263`

**Problem**: The CLI serialises apply results as `Vec<(PluginMetadata, ApplyResult)>` (array of
2-tuples), but the Tauri backend deserialises them as `Vec<ApplyResult>` (flat array). These types
do not match. `serde_json::from_str` always fails with a type error.

**Impact**: Even when the CLI successfully applies all hardening changes to the system, the GUI
always receives `Err("Failed to parse apply results: ...")`. The user sees nothing. Hardening
DID happen on disk, but the GUI reports failure and never shows results.

**Fix**: Either change the CLI to emit `Vec<ApplyResult>` only, or change the Tauri command to
deserialise `Vec<(PluginMetadata, ApplyResult)>` and extract the results.

---

### BUG-02: Tauri Parameter Name Mismatch (camelCase vs snake_case) — FIXED

**Severity**: CRITICAL | **Status**: Fixed (commit b9ce945)
**Files**:
- `crates/hardener-ui/src/tauri_bindings.rs:64-66`
- `src-tauri/src/commands.rs:241`

**Problem**: The WASM frontend sends `{"pluginIds": [...]}` (camelCase) but the Tauri command
expects `plugin_ids` (snake_case). Tauri v2's default deserialisation may fail to map these,
resulting in an empty vector being received.

**Impact**: When user clicks "Preview Changes" or "Confirm & Apply", the plugin list arrives
empty. The CLI receives `hardener apply --format json` with no `--plugin` flags, rejects it
with "Specify plugins with --plugin or use --all", and nothing happens.

**Affected functions**:
- `invoke_apply()` - sends `"pluginIds"` (line 65)
- `invoke_apply_dry_run()` - sends `"pluginIds"` (line 82)
- `invoke_rollback()` - sends `"checkpointId"` (line 135)

**Fix**: Change all parameter names to snake_case: `"plugin_ids"`, `"checkpoint_id"`.

### BUG-03: All GUI Errors Are Invisible to the User — FIXED

**Severity**: CRITICAL | **Status**: Fixed (commit b9ce945)
**Files**:
- `crates/hardener-ui/src/components/configure_section.rs:144-146`
- `crates/hardener-ui/src/components/quick_actions.rs:49-51`
- `crates/hardener-ui/src/components/analysis_page.rs:38-40`
- `crates/hardener-ui/src/components/history_section.rs:27-29, 51-53`

**Problem**: Every `Err` branch across the entire frontend only calls
`web_sys::console::error_1(...)`. There is no toast, modal, inline message, or any visible
UI feedback. The user sees the button re-enable and nothing else.

**Impact**: When BUG-01 or BUG-02 causes apply to fail, the user has zero indication of what
went wrong. They must open browser dev tools to see the error in the console.

**Fix**: Add an `error_message: RwSignal<Option<String>>` to `AppState` and render a visible
error notification component. Set it in every error handler.

### BUG-04: UFW Firewall Backend Applies Wrong Rules — FIXED

**Severity**: CRITICAL | **Status**: Fixed (commit b9ce945)
**File**: `crates/hardener-plugins/src/firewall/ufw.rs:95-101`

**Problem**: The `build_ufw_rule_args()` method matches against `rule.rule_description`
(a human-readable string like "Allow loopback traffic") instead of `rule.rule_action`
(the actual action: "accept", "drop", "reject"). Since descriptions never equal "accept"
or "drop", the match falls through to `_ => "deny"`.

**Impact**: Every firewall rule generated by the UFW backend becomes a `deny` rule, regardless
of intended action. "Allow SSH" becomes `ufw deny 22/tcp` - potentially locking out SSH access.
This is a dangerous silent logic bug.

**Fix**: Change `rule.rule_description.as_str()` to `rule.rule_action.as_str()` on line 95.

---

### BUG-05: Firewall Plugin Hardcodes `apply_success: true` — FIXED

**Severity**: HIGH | **Status**: Fixed (commit b9ce945)
**File**: `crates/hardener-plugins/src/firewall/mod.rs:335-341`

**Problem**: The firewall plugin's `apply()` returns `apply_success: true` regardless of
whether individual changes succeeded. All other plugins use
`apply_changes.iter().all(|c| c.change_success)`.

**Impact**: Even if every firewall rule fails to apply, the CLI reports success with a green
checkmark. Combined with BUG-04, the user sees "Firewall Hardening - Success" when all rules
were applied as deny instead of allow.

**Fix**: Replace `apply_success: true` with
`apply_success: apply_changes.iter().all(|c| c.change_success)`.

---

### BUG-06: CLI Apply Always Exits 0, Even on Total Failure — FIXED

**Severity**: HIGH | **Status**: Fixed (commit b9ce945)
**File**: `crates/hardener-cli/src/commands/apply.rs:81-129`

**Problem**: The apply command loop catches per-plugin errors with `output::error(...)` but
continues to the next plugin. After all plugins, it returns `Ok(())` unconditionally. The
process exits with code 0 even if every single plugin failed.

**Impact**: Any automation, CI/CD, or the Tauri backend that checks the exit code will
believe apply succeeded. The Tauri backend only checks if the subprocess exited 0 to determine
success.

**Fix**: Track whether any plugin failed and return a non-zero exit code.

## TIER 2: MAJOR BUGS (Functionality Broken)

### BUG-07: `Config` Struct Is Empty - No Configuration Loading for Apply — FIXED

**Severity**: HIGH | **Status**: Fixed (commit b9ce945)
**Files**:
- `crates/hardener-cli/src/commands/apply.rs:53`
- `crates/hardener-core/src/plugin.rs:29-31`

**Problem**: The apply command creates `let config = Config;` - a completely empty unit struct.
The rich `HardenerConfig` with per-plugin directives, enabled/disabled flags, and policy
exceptions is never loaded. The `--config` CLI flag is accepted but ignored.

**Impact**: Custom configuration has no effect on apply. Disabled plugins still run.
Policy exceptions are not honoured.

**Fix**: Load `HardenerConfig` via `ConfigLoader` (same pattern as `scan.rs:91-103`) and pass
it to plugins.

---

### BUG-08: Rollback Panics with Nested Tokio Runtime — FIXED

**Severity**: HIGH | **Status**: Fixed (prior session, commit bb124a5)
**File**: `crates/hardener-plugins/src/lib.rs:29-37`

**Problem**: `rollback_files_from_checkpoint()` creates a new `tokio::runtime::Runtime` and
calls `block_on()` inside an already-running Tokio runtime. This panics with "Cannot start a
runtime from within a runtime" on all modern Tokio versions.

**Impact**: Rollback is completely broken for 7 out of 8 plugins (SSH, PAM, MAC, Audit,
Permissions, Services, Firewall). Only the kernel plugin works because it uses async directly.

**Note**: NEXT.md documents this as "Bug P - FIXED" but the fix may not be committed yet.
Verify the current state of this file.

**Fix**: Make `rollback_files_from_checkpoint()` async and use `.await` at all 7 call sites.

---

### BUG-09: Binary Discovery Fails in Development

**Severity**: HIGH
**File**: `src-tauri/src/commands.rs:35-58`

**Problem**: `get_hardener_binary_path()` looks for `hardener` in the same directory as the
Tauri executable. In development, the Tauri binary is at `target/debug/linux-system-hardener`
but the CLI binary is `target/debug/hardener` - and it must be separately built. If not found,
it falls back to `which hardener` in PATH.

**Impact**: If the CLI binary hasn't been built or isn't on PATH, all GUI apply/rollback
operations fail with "Could not find hardener binary". This error goes to the console only
(BUG-03).

**Fix**: Improve binary discovery with explicit build instructions, or build both binaries
together in the workspace.

---

### BUG-10: PAM Plugin Bypasses the Executor Abstraction

**Severity**: MEDIUM
**File**: `crates/hardener-plugins/src/pam/mod.rs:324-352`

**Problem**: The PAM plugin uses `update_file_atomically()` (direct `std::fs::write`) instead
of `ctx.executor().write_file()`. This bypasses the SSH executor entirely.

**Impact**: PAM hardening cannot work on remote systems. It also bypasses the MockExecutor,
making the PAM plugin untestable. A backup may be created (via executor) but the new config
write fails if not root, leaving the system in an inconsistent state.

**Fix**: Replace `update_file_atomically()` calls with `ctx.executor().write_file()`.

---

### BUG-11: Checkpoint Database Path Divergence — PARTIALLY FIXED

**Severity**: MEDIUM | **Status**: Partially fixed (prior session — GUI reads both DBs)
**File**: `src-tauri/src/commands.rs:141-151`

**Problem**: When the CLI runs under pkexec (as root), `dirs::data_local_dir()` resolves to
`/root/.local/share/linux-hardener/checkpoints.db`. The Tauri process (desktop user) cannot
read this path. The system path `/var/lib/linux-hardener/checkpoints.db` is checked by the
GUI's `get_checkpoints` but not consistently used by the CLI apply.

**Impact**: Checkpoints created during apply are invisible to the GUI. The History tab shows
no checkpoints after a successful apply.

**Fix**: Establish a single canonical system path and use it consistently.

---

### BUG-12: `sshd.config` Typo in Checkpoint Path — FIXED

**Severity**: MEDIUM | **Status**: Fixed (commit 0d55037)
**File**: `crates/hardener-cli/src/commands/checkpoint.rs:98`

**Problem**: The manual checkpoint path list uses `/etc/ssh/sshd.config` (with a dot) instead
of `/etc/ssh/sshd_config` (with an underscore).

**Impact**: Manual checkpoints via `hardener checkpoint create` will never snapshot the SSH
configuration file. Plugin-created checkpoints are unaffected (they use their own paths).

**Fix**: Change `sshd.config` to `sshd_config`.

---

### BUG-13: Timestamp Formatting Uses Debug Format — FIXED

**Severity**: LOW | **Status**: Fixed (commit 0d55037)
**File**: `src-tauri/src/commands.rs:23-28`

**Problem**: `format!("{:?}", datetime)` on a `SystemTime` produces
`"SystemTime { tv_sec: ..., tv_nsec: ... }"` instead of a human-readable date.

**Impact**: The History tab's "Created" column shows unreadable raw values.

**Fix**: Use `chrono`-based formatting matching the CLI's `output.rs:257-266`.
